Lesson 1 · 30 minutes

Context and memory: what your agent sees, and what it remembers

By the end of this lesson you can take a request your makerspace assistant handles — like "Can I book the laser cutter Friday, and do I still need safety training?" — and sort every piece of information it needs into three buckets, with a reason for each. The buckets: what lives in context for this turn, what gets saved as a note for next session, and what gets retrieved from a manual on demand.

Objective O3: explain context and memory — the context window, what carries forward within and between sessions, and retrieval and notes as memory About 30 minutes Builds on your agent-loop session (recap below)
Why this matters for you

Your senior design team's assistant has to answer from long machine manuals and remember which students have finished safety training, across separate visits — all on a sponsor's small model budget. What it keeps in context, what it saves, and how it finds the right manual page is exactly what you need to decide before your design review.

Whatever text it's given as input — the floor everything else sits on. Today that input gets a name: the context window.

Recall — the agent loop

Check your answer

It builds on what came before: each step's result feeds into the next. Today you'll see exactly how far "before" reaches, and where it stops.

A. What's in the context window right now 4 min

Every message, instruction and result passes through the model as tokens: small chunks of text, often a piece of a word rather than a whole one. The context window is all the tokens the model can reference while generating one response — the system prompt, the whole conversation so far, the tool definitions it was given, the results tools have already returned, and the output it's writing now (Context windows, Claude docs).

It's a working memory for this one turn — completely separate from what the model learned during training. Training shaped how the model predicts its next token; the context window is what it's actually looking at right now to make that prediction.

Nothing in training is "in context." A model can know a fact from training and still not have it in front of it this turn — that gap is exactly why the rest of this lesson matters.

Think about a program running on a machine. RAM is whatever the program is actively working with right now — load something into RAM and it's part of the computation; leave it sitting on disk and it isn't, no matter how relevant it might be. The context window is RAM for your makerspace assistant.

The model's training is like software already compiled into the machine: baked in, not something you load fresh each run. A page of the safety manual nobody has opened yet just sits on disk — present somewhere on the system, but not in the program's working memory until something actually reads it in.

For the Friday laser-cutter request, this turn's context window holds the system prompt describing the assistant's job, the student's question, the tool definition for checking the booking calendar, and whatever the calendar tool just returned. It does not hold the whole safety manual — only whichever page, if any, got pulled in for this specific turn.

Check yourself

For the Friday laser-cutter request, which of these actually counts toward the context window for this turn?

Show the answer

The tool definitions and the calendar's result are right: they were actually sent to the model this turn. The manual and the training-history options describe things that could matter in general, but "could matter" is not the same as "was in the prompt" — only what was actually sent counts as context.

B. What carries forward, step to step 3 min

Within one running session, the default is simple: nothing mid-session gets quietly dropped. Each new step's input is everything that came before, plus whatever is newest — so earlier tool results stay visible for the rest of that session unless something explicitly removes them (Context windows, Claude docs).

Recall the Friday-booking trace from your agent-loop session: step 1 asks the calendar tool whether the laser cutter is free, step 2 checks whether the student still needs safety training, step 3 gives the final answer. At step 3, the model doesn't just see this step's question — it still sees the original question, step 1's tool call and result, and step 2's tool call and result. None of that was removed along the way.

That's why an agent can reason about something a tool told it three steps ago without re-asking: the result never left context in the first place. Picture it as RAM that only grows during a session — nothing gets freed until the session itself ends.

"By default" matters here. Some systems do deliberately trim or summarize older turns — but that's a choice someone made, not something that happens automatically.
A common mix-up

"Only the latest tool result matters mid-session" is tempting because the agent seems to move on after each step, result in hand. But by default every earlier turn in the same session stays in context too — step 1's result is just as visible at step 3 as step 2's is, nothing mid-session gets quietly dropped.

One consequence: the longer a session runs, the more tokens are sitting in its context window, since step 1's content never disappears on its own. That's harmless for a short exchange, but it starts to matter once a session runs long — which is exactly where the next section picks up.

Check yourself

Back to the Friday-booking trace: is the step-1 calendar result still visible to the model while it's working on step 3, in the same run?

Show the answer

Yes, it's still visible. By default, every earlier turn in a session — including step 1's tool result — stays in the context window for every later step in that same session.

C. Limits and context rot 5 min

The context window isn't unlimited. It has a fixed size, measured in tokens, shared between what goes in and what comes out. If the input alone already fills it, the request fails outright, before the model generates anything. If the model is still writing when the window fills up, the output just stops mid-sentence (Context windows, Claude docs).

Check yourself

Someone pastes the entire 300-page safety manual, plus the full conversation so far, into one request — and the total is bigger than the context window's limit. What happens?

Show the answer

It fails outright. Input and output share one fixed token budget, so if the input alone is already over the limit, the request never gets to the point of generating a response.

Fixed size isn't the only limit worth knowing. As the number of tokens in context grows, accuracy and recall tend to get worse — a pattern called context rot. More context is not automatically better: what's in the window matters as much as how much room is left in it (Context windows, Claude docs).

Same RAM picture from Section A: a machine bogs down and starts making mistakes once it's crammed with old, irrelevant files, even though technically there's still room. A machine kept tidy — just what's needed, loaded on purpose — runs faster and more reliably. Your assistant's context window behaves the same way.

A common mix-up

"A bigger context window always gives a better answer" is tempting — more capacity sounds like it can only help. But context rot means stuffing in more, including old, irrelevant history, can make the model less accurate, not more. Capacity is not the same as quality.

For your assistant, that's two separate reasons to be deliberate about what's in context: a full window breaks the request outright, and a crowded one — even one well short of full — can quietly make answers worse.

Check yourself

The assistant's context is nearly full of old, unrelated chat turns from earlier students. Does piling on more of that history make its next answer more reliable?

Show the answer

No, it doesn't. Past a point, extra tokens — especially irrelevant ones — degrade accuracy rather than improve it, and that effect (context rot) shows up well before the window physically runs out of room.

D. Between sessions: nothing survives unless saved 4 min

When a session ends, its context window is gone. So across a new session, the assistant doesn't "remember" anything from before unless something wrote it to storage outside the context window first, and a later session reads it back in — otherwise that progress is simply lost (Memory tool, Claude docs). That reading-back-in is what people mean by an agent's memory: not a property of the model itself, but information deliberately saved outside the window and retrieved later.

Think about working out a recipe tweak in your head while cooking — a little more salt, a little less time in the oven. Leave the kitchen without writing it down, and that adjustment is just gone; next time you're guessing again. Write it on an index card, though, and future-you can read the card back and skip the guesswork.

A common mix-up

"The assistant remembers earlier conversations the way a person would" feels true because talking to it across visits feels continuous. But every session's context window starts empty. Anything that feels like memory was written to storage and read back in — or it simply isn't there.

This is also the budget story: paying to re-explain the same facts every session would burn through your sponsor's model budget fast. Saving a fact once, outside the window, is cheaper than re-deriving it every visit.

Check yourself

A student finished laser safety training yesterday and comes back today, in a brand-new session. If nothing was saved, does the assistant know?

Show the answer

No, it doesn't — not unless something saved it. A new session's context window starts empty; the only way the assistant "knows" is if yesterday's session (or the system behind it) wrote the fact to storage and today's session reads it back.

E. Notes as memory 4 min

The mechanism behind that saved record is simple: the agent itself writes what it learns — facts, decisions, progress — to a file or a database outside the context window, and reads it back in during a later session. This pattern is usually called notes as memory: building knowledge over time without ever having to keep everything loaded at once (Memory tool, Claude docs).

A common mix-up

"The context window and memory are the same thing" is an easy slip — both answer "what does the assistant know right now?" But they're not the same storage: the context window is temporary and wiped clean at the end of every session (Sections A–D), while a note is durable storage the assistant deliberately writes to and reads back, living entirely outside the window. A note is how something earns its way back into a future session's context window — it isn't the window itself.

Same index-card idea, pointed at your assistant. When a student finishes safety training, the assistant (or the booking system behind it) writes something like "student finished laser safety training on Nov 20" to a saved record — a file, or a row in a database, outside any context window. Next visit, a brand-new session starts, but its first steps can read that record back in. The assistant looks like it "remembers," without ever reloading months of old conversation.

Notice this is a choice the agent (or its designer) makes on purpose — nothing gets saved automatically just because it happened in a session.

Not everything belongs in a note. A note is for durable facts worth having next time — a training date, a decision, a standing preference. The exact wording of today's question isn't worth saving; it's only useful for this turn, and saving everything would just drag context rot into your saved memory too.

Check yourself

A student asks, "Can I finally book the laser cutter now that I've finished training?" Which piece belongs in a saved note for next session: the exact wording of today's question, or the date training was completed?

Show the answer

The training completion date belongs in the note. It's a durable fact the assistant needs again later; today's exact wording is only useful for this one turn and isn't worth saving.

Notes solve "what happened before." They don't solve a different problem: a 300-page manual too big to ever fully load. That's next.

F. Retrieval: finding the right page on demand 5 min

Retrieval — the "R" in the technique often called RAG, retrieval-augmented generation — means searching a large external source for just the part relevant to the current request, and adding only that part to the prompt, instead of loading the whole source (What is Retrieval Augmented Generation?, IBM).

The reason to bother: because retrieval only pulls in the one matching passage, the assistant can work from manuals far larger than any single prompt's fixed token budget could hold (Section C). And when the manual gets revised, there's nothing to retrain — the next search just finds the updated passage instead, without the model ever needing to learn the change (What is RAG?, AWS). The knowledge stays external and gets pulled in only when it's actually needed.

You've built lookups by key in Python before — a dictionary where you fetch one record instead of scanning a whole list. Retrieval does the same thing at the document level: index the source once, then fetch just the passage that matches the current query, instead of scanning or loading the whole thing every time.

A common mix-up

"Retrieval means handing the model the whole document" is a tempting read of "giving the model access to a source" — access sounds like everything. But retrieval's whole point is to pull in only the relevant slice, so the context window never has to hold the whole source at once.

Picture your 300-page laser cutter manual. You wouldn't read the entire book to answer "how often does the lens need cleaning?" — you'd check the index for "lens maintenance" and read that one page. Retrieval gives the assistant the same shortcut: it searches the manual for the passage about lens maintenance, and only that passage lands in this turn's context window. The other 299 pages stay right where they are, unread, until something else needs them.

You now have three buckets for anything the assistant needs: in context this turn, saved as a note, or retrieved on demand. Time to sort a real request into them.

Check yourself

To let the assistant answer from a 300-page manual, should every prompt include the whole manual, or should the assistant retrieve just the relevant page?

Show the answer

Retrieve only the relevant page. That keeps the context window small and lets the assistant answer from material that's far bigger than the window — and stays current, since retrieval always searches the latest version of the manual.

Worked example and practice 6 min

This is the sorting skill from this lesson's win, applied to one real request. Four pieces of information, three buckets — work through the reasoning for each.

Worked example

The request: "Can I book the laser cutter Friday afternoon, and do I still need to retake safety training?" The assistant has four pieces of information available:

  1. the student's question, just typed
  2. the booking calendar's result for Friday
  3. the laser cutter manual's section on safety-retraining intervals
  4. the student's safety-training completion date, from their last visit

Let's classify the first two.

  1. Item 1, the question: context window, for this turn. It's the newest message, the thing that kicked off this step — by definition, it's part of this turn's input (Section A).
  2. Item 2, the calendar result: context window, for this turn. The assistant called the calendar tool as part of answering this request, and the result came back into this same session's context — it hasn't gone anywhere (Section B).
Your turn

Now classify items 3 and 4. For each, say which bucket it belongs in — context window, note, or retrieval — and why.

  • Item 3: the manual's safety-retraining-interval section. (Hint: think back to Section F.)
  • Item 4: the student's training completion date from their last visit. (Hint: think back to Section E.)
Show a solution

Item 3 — retrieval. The manual is a large external source the assistant doesn't carry around in context by default; it's searched for the one relevant section (safety-retraining intervals) only when a request calls for it, and only that section gets added to this turn's prompt.

Item 4 — a saved note. The training date came from a past session that no longer exists. It's only available now because something wrote it to storage after that visit, and this turn reads it back in — the notes-as-memory pattern from Section E, not something freshly searched for in a manual or sitting natively in context.

Notice the pattern: the context window holds whatever this turn's input actually contained; a note holds a durable fact from a session that's already gone; retrieval holds whatever a large external source can hand over on demand. Nothing is in two buckets for the same reason twice.

Bonus: a trickier case

If the assistant also needs to know the makerspace's holiday closures (the same every year), where would that fact best live? A note — it's durable and doesn't change per request, so it's wasteful to retrieve or re-derive it every time. But it also isn't something generated fresh in conversation, so it isn't "context" either; it's exactly the kind of fact worth writing down once and reading back forever.

That's the whole skill: for anything your assistant needs, ask where it came from and how long it has to last — the answer sorts it into one of the three buckets.

Summary 2 min

  • The context window is everything actually sent to the model this turn — system prompt, conversation, tool definitions and results, output — not what it learned in training.
  • Within one session, every earlier turn stays in context by default; across sessions, nothing survives unless it was written to storage and read back in.
  • More context isn't automatically better: context rot means irrelevant tokens can make answers worse well before the window is even full.
  • A note is a durable fact the agent deliberately saves outside context and reads back later; retrieval is searching a large external source for just the relevant slice, on demand.
  • Every token in context costs money and attention, so being deliberate about what's in context, saved, or retrieved is also how you keep your assistant within a small model budget.
