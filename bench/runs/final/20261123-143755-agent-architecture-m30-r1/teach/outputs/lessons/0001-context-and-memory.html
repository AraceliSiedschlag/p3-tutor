Context and memory: what your agent actually remembers

By the end of this lesson, you can trace one makerspace-assistant request and say exactly where each piece of information lives — in the context window for that call, resent on the next step, saved to a file between visits, or pulled in by retrieval when needed — and use that to decide what the assistant must save between visits.

Objective O3: context, memory, retrieval and notes in an agent About 30 minutes
Why this matters for you

Your makerspace assistant has to answer from manuals far too long to fit in one call, and remember each student's training status across visits days apart. Today you'll nail down exactly what it keeps, what it forgets, and what you have to design it to save.

The context window: working memory for one call 4 min

Every call to the model arrives with a pile of text: the system prompt (its instructions), the conversation so far, the tools it's allowed to use, and any tool result already returned this call. All of that together is the context window — every token the model processes for this one call (Anthropic, Context windows).

That text is measured in tokens: a token is roughly a word or a word-piece — "to" is one token, "antidisestablishmentarianism" is several. The context window has a fixed size in tokens, and every token inside it, whatever its source, counts against that same limit.

All of this happens inside one session: one continuous run of the assistant, from when it starts handling a request to when it stops. What's kept inside a session, and what survives into the next one, is exactly what the next few sections sort out.

Here's the part that matters most: nothing outside that window exists to the model at that moment. Not the student it talked to yesterday, not next week's calendar, not the rest of a manual sitting in a folder somewhere — unless that text was placed into this call, the model has no access to it at all.

Think of the context window as everything printed out and handed to the model right before it answers. If it isn't in that stack of paper, the model can't see it.

Picture an IT help-desk ticket. A technician picking it up can only act on what's typed into that ticket's thread, not the whole company wiki, unless someone pastes a relevant snippet into the thread. Your makerspace assistant works the same way: it can only act on what's sitting in its current call, not the entire manual library, unless a chunk of a manual gets placed there by a tool call.

Check yourself

The assistant is mid-call, answering a student's question about the drill press. Which of these is actually in its context window right now?

Show the answer

The system prompt, the student's question, and any tool result already returned this call — that's the only text in context right now. The other two options describe things that exist somewhere but were never sent as input to this call.

What's kept between steps: resent, not remembered 3 min

Within one session, each new step doesn't add to some memory inside the model — it resends everything. The program collects the full history so far (every earlier turn and every tool result) and sends that whole stack again as input to the next call (Anthropic, Context windows).

The model itself holds nothing between calls. It isn't that it forgets slowly — it has no state left over from the last call at all. Only the program carries anything forward, by appending the latest turn and sending the growing pile back in.

You've seen this pattern before: a reply-all email thread. Every new message carries the whole quoted history underneath it, so the fifth reply still shows the first message, in full. Nothing was "remembered" — it was just quoted in again, every single time. Your makerspace assistant does the same: it resends the student's question, the tool call it made, and that tool's result, at every step of the loop.

A common mix-up

It's tempting to think the model "remembers" what you told it a minute ago, the same way training works — it clearly uses what you just said. But the model's weights never change mid-conversation. It only has that text because it's sitting in the current context window, freshly resent; take it out of the resend, and the model has no idea it ever happened. This builds on what you already know: training knowledge is fixed, everything else is just what's in the text it's given.

Check yourself

The assistant looks up the laser cutter's free slot on Friday, then a moment later answers a follow-up question about that same slot. Does it answer the follow-up correctly because it remembers the lookup, or because the lookup's result got resent as text?

Show the answer

The lookup's result was resent as plain text along with everything else in the history. The model answers the follow-up correctly because that text is sitting right there in the new call's context, not because it remembers anything.

Why fuller isn't free: context rot and cost 4 min

The context window has a fixed size in tokens, and here's the part that surprises people: stuffing more into it doesn't make the model more capable. Past a point, recall accuracy actually gets worse as the token count grows — an effect called context rot (Anthropic, Effective context engineering for AI agents).

So curating what goes in matters as much as how much room there is. A context window crammed with everything that might be relevant makes it harder, not easier, for the model to find the one fact it actually needs for this answer.

There's a second cost, separate from accuracy: every token in the context window, whatever its source, counts against the same size limit and the same per-token price. History, a retrieved page, a loaded note — all billed the same way (Anthropic, Context windows). What the assistant keeps in context at each step drives both whether it gets the right answer and what the request costs, which matters directly for your team's small model budget.

Think about cooking with every spice jar in the house pulled out onto the counter. Finding the salt is slower with forty jars crowding the counter than with the three jars today's recipe actually needs. A context window stuffed with six past conversations and a whole manual works the same way: more sitting there makes the one fact harder to find, not easier.

A common mix-up

A bigger context window means you can just keep everything in it and skip memory design. More room does sound like fewer limits. But recall degrades as the window fills, and every extra token costs money — so even a 1-million-token window still rewards deciding what belongs in context right now versus what should be fetched or noted only when it's needed.

Check yourself

The assistant's context has grown to include six past students' entire conversations. If you add today's manual pages on top of that, without removing anything, will today's answer get more reliable, less reliable, or stay about the same?

Show the answer

Less reliable. The six old conversations are clutter on top of today's manual pages, and context rot means recall gets worse as the window fills, not better — on top of paying for every extra token.

What's kept between sessions: nothing, unless it's saved 3 min

Everything so far happened inside one session. Start a new session, and the story changes completely: the context window opens empty. Nothing from an earlier session is automatically there (Helix DB, LLM memory architecture; corroborated by Anthropic's memory tool docs).

Anything the assistant needs across that gap has to be written to storage outside the model — a file, a database row — and then deliberately read back in at the start of the next session. If no one wrote it down, and no one reads it back, it's gone.

Rebooting a computer clears whatever was sitting in RAM; only what got saved to disk survives the restart. A new chat session is a reboot of the model's working memory — only what the assistant actually wrote to a file survives into the next one.

A common mix-up

A new session should pick up where the last one left off, like a phone call you can resume. Within one session, history clearly does carry forward turn to turn, which makes it feel continuous — but that continuity stops the moment the session ends. A new session only continues if something explicitly saved state to a file, and the new session explicitly reads that file back.

Check yourself

A student asks about the drill press on Monday, in one session. On Wednesday, they open a new session and ask a follow-up. Does the assistant still have Monday's conversation unless something was done to save it?

Show the answer

No. Wednesday's session opens with an empty context window. Monday's conversation only comes back if something saved it to a file on Monday and something reads that file back on Wednesday.

Notes: the agent's own saved state 4 min

Notes (also called memory files) are text the agent itself writes to storage outside the context window — a to-do list, a status file — specifically so a later step or a later session can read it back and pick up where it left off (Anthropic, Effective context engineering for AI agents; mechanics in the memory tool docs).

The key word is "itself." A note isn't a pre-existing document the assistant looks up; it's something the assistant observed or decided, and chose to write down for its own future use.

Mechanically, writing a note is just another tool call: the model asks to write some text to a file, the program saves it, and that's it until something reads the file again. What makes it a note, rather than retrieval, is that the agent generated the content itself, not that it's stored in any particular way.

A kitchen journal works the same way. After a bake that came out dense, you jot down "ran out of flour, substituted X, came out dense," and you reread that entry before the next bake. Your makerspace assistant does the same thing: it writes "Priya passed laser training on Nov 10" to a student-status file, and rereads that file the next time Priya asks to book the laser cutter.

A note only matters again if something reads the file back into context later. Writing it isn't enough on its own — the next session, or the next step, has to load it.
Check yourself

After the assistant writes that note about Priya and the session ends, is the fact now part of the model's trained knowledge — usable for any future question without opening the file?

Show the answer

No. The fact is only a line in a file. It has no effect on the model at all until some step reads that file and puts its contents back into a context window.

Retrieval: pulling in a source just in time 3 min

Retrieval is fetching one specific piece of a larger existing source — a page of a manual, a row of a calendar — into context only when it's actually needed, instead of keeping the whole source loaded all the time (Anthropic, Effective context engineering for AI agents). This is sometimes called "just-in-time" loading.

The source already existed before the agent ever touched it — a manual someone wrote, a calendar someone maintains. Retrieval doesn't create that content; it just brings the relevant slice of it into the current call. Mechanically it's a tool call like any other: the model asks for the page, a program goes and gets it, and the result comes back as part of this call's context.

Retrieval doesn't just protect accuracy, it protects your budget too. A tool call that returns one page costs roughly as many tokens as that page has words; a tool call that dumps the whole manual in costs roughly as many tokens as the whole manual has words, every single time it happens, whether or not the question actually needed it.

If you've queried a database, you already do this: you pull one row with a WHERE clause instead of loading the entire table into memory. Your makerspace assistant does the same thing with the drill press manual — it fetches page 42 for the torque spec, not the whole 80-page document.

Check yourself

Should the assistant keep the full 80-page manual in context on every call, or fetch just the relevant page when a question needs it?

Show the answer

Fetch just the relevant page. That's exactly what retrieval is for: the right fact, pulled in only when it's needed, at a fraction of the cost of loading the whole source every time.

Retrieval vs. notes, side by side 3 min

Retrieval and notes look identical from the model's point of view: both are a tool call that returns some text, and that text lands in the context window the same way (Anthropic, Memory tool docs). The difference is where that text came from.

Retrieval reads something that already existed before the agent got involved: a manual, a policy page, a calendar. Notes read something the agent itself recorded earlier: a status it observed, a decision it made, written down specifically so a later step could use it (Anthropic, Effective context engineering for AI agents).

FeatureRetrievalNotes
SourceAn existing document or recordThe agent's own observation or decision
ExampleThe drill press manual's torque spec"Priya passed laser training on Nov 10"
WrittenBefore the agent ever ranBy the agent, during an earlier step or session

In IT terms: looking up the company's existing password-reset policy page is retrieval, since that page was written long before any ticket came in. Writing a note in a ticket for the next technician, "customer prefers callbacks after 5pm," is a note, since nothing like it existed until someone wrote it. Both get read back later; only one of them already existed.

A common mix-up

Retrieval and notes are basically the same feature, since both show up as a tool call returning text. Mechanically, sure — but the source is different every time: retrieval reaches an existing external document, notes are the agent's own record of something it saw or decided. Mixing them up means trusting a guess (a note) where you needed a fact (a retrieval), or the reverse.

Check yourself

The assistant needs the drill press's torque spec. Should it (a) keep the whole manual in context every turn, (b) retrieve just that page when asked, or (c) write a note guessing the number from memory?

Show the answer

Retrieve just that page. It's the only option that gets a real, checkable number, and it does so cheaply, without loading content the question doesn't need.

Worked example and practice 4 min

Worked example

A student asks, in one session: "Is the laser cutter free Friday, and am I trained on it?" Trace what happens to every piece of information involved.

  1. The question enters context. It's the first text in this call: part of the "conversation so far."
  2. The assistant calls the booking-calendar tool to check Friday. That's retrieval: pulling in a slice of a calendar that already existed. The result, "Friday 2–5pm open," is added to context.
  3. For the next step, the program resends everything so far — question, tool call, result — plus a new call to read the student's training-status file. That file read is mechanically a retrieval call. But what's inside the file is a note: something the agent itself wrote earlier, not a pre-existing document.
  4. With both results sitting in context, the model gives its final answer: "Yes, Friday 2–5pm is open, and your training note shows you passed on Nov 10 — you're clear to book."
  5. Days later, session two: the student asks, "Can I still book Friday?" The context window opens empty; nothing from session one is there automatically.
  6. Before it can answer, the assistant has to read the training-status file again, and recheck the calendar, not because anything changed, but because nothing survives a new session unless it's reloaded.

  1. The question enters context: this is the first text in the call.
  2. The assistant checks what's already in context. In a fresh session, nothing is there yet, so every fact needs a tool call.

Now you fill in: which step is a retrieval call, which step is a note being read, and what happens if the student comes back tomorrow in a new session.

Show a solution
  1. The assistant calls the booking-calendar tool to check Thursday for the 3D printer. That's retrieval of an existing source; the result goes into context.
  2. The assistant reads the student's safety-module status file. That file was written earlier by the assistant itself, so reading it is retrieval of a note.
  3. With both results in context, the model answers: whether Thursday is open, and whether the safety module shows complete.
  4. Tomorrow, in a new session, the context window opens empty again. Both the calendar check and the safety-module file read have to happen again — nothing from today carries over unless it was saved, and both of these were only ever read, not newly saved, so they simply get re-fetched.

Summary 1 min

  • The context window is the model's whole working memory for one call; nothing outside it exists to the model right then.
  • Within a session, every step resends the full history so far; the model itself keeps nothing between calls.
  • Across sessions, nothing survives unless it was written to a file and read back in; a new session starts empty.
  • Retrieval pulls in a slice of something that already existed, on demand; notes are something the agent itself wrote down for later.
  • Every token in context, whether history, a retrieved chunk, or a loaded note, counts against the same size limit and the same cost.
