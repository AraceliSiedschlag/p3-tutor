What your assistant remembers: context, retrieval and memory

By the end of this lesson you can trace, for any point in a student's visit to your makerspace assistant, exactly what the model can see right now, what will still be true at their next visit, and how the assistant finds one page in a two-hundred-page manual without pasting the whole manual into the prompt.

Objective O3: context, memory and retrieval in an agent About 30 minutes
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both are the same underlying question: what does the model see this call, and what survives after the call ends? Get this wrong and your assistant either forgets a student it just trained, or burns your sponsor's budget re-reading a whole manual on every question.

Warm-up 2 min

Recall

Last time, you traced a request to the makerspace assistant: the model asked for check_calendar, the program ran it, and the result went back to the model. Once that result is sent back, where does it go, and does the model keep seeing it for the rest of that run?

Check your answer

It gets added to what the model is given on its next call — and every call after that in the same run, not just the one right after. That growing pile of text the model is handed, call after call, is this lesson's whole subject: the context window. Today you'll see exactly what piles up in it, what falls out of it, and how your assistant can still act as if it "remembers" something that isn't in it any more.

The context window 5 min

Picture handing a colleague a printed transcript of a conversation and asking them to write the next line, then throwing the transcript away and handing them a fresh printout — the old one plus one more page stapled on — for the next line after that. They never "remember" the conversation between hand-offs; they only know what's on the pages you physically give them each time. That stack of pages, handed over fresh on every single call, is what a language model works from.

The context window is the full set of text given to the model for one call: its instructions, the conversation so far, and every tool result so far. The model only knows what's on those pages — nothing before them, nothing outside them, however confidently it writes (Anthropic, "Effective context engineering for AI agents," 2025).

Text is measured in tokens, roughly three-quarters of a word each. The context window has a fixed maximum number of tokens, and tokens are also most of what a call costs: more pages handed over, more tokens billed, every single call. Past a certain point, stuffing in more also backfires on quality, not just cost: Anthropic calls this context rot — as the pile of text grows, the model's grip on any one fact inside it gets looser, the same way a fact buried on page 80 of a handed-over transcript is easier to miss than one on page 1 (Anthropic, 2025).

A common mix-up

It's tempting to treat the context window as a free filing cabinet: when in doubt, stuff in more, just in case. It isn't free. Every token you keep around is sent, and billed, on every remaining call in that run, and past some point it makes the model's recall worse, not better. On a sponsor's small budget, the context window is something to spend on purpose, not a place to dump everything that might be relevant.

What stays in view within a session 4 min

Trace Monday's laser-cutter question again, call by call. Call 1 is handed: the instructions, plus "Is the laser cutter free Friday?" Call 2 is handed all of that, plus the result of check_calendar. Call 3 is handed all of that, plus the result of search_manuals. Nothing from earlier calls is dropped on its own; the context window within one session only grows, one stapled-on page at a time, exactly as Figure 1 showed.

That growth has a practical ceiling. If a session runs very long — many back-and-forth tool calls on one hard printer fault, say — the transcript will eventually threaten the limit. The common fix is compaction: before the limit is hit, the program asks the model to summarize everything so far into a short note, then continues the next call from that summary instead of the full transcript. Claude Code's own agent does this, keeping "architectural decisions, unresolved bugs, and implementation details" and dropping redundant back-and-forth (Anthropic, 2025). For your assistant, the same move would turn ten exchanges of printer-fault troubleshooting into three sentences of "what's been tried, what's left," then carry on.

Compaction is a deliberate, designed step the program takes — it does not happen by itself, and it is a different thing from the model simply "forgetting": the information is kept, just compressed.
Check yourself

A student's 3D-print troubleshooting session has run through a dozen tool calls and is approaching the context limit. The assistant still needs several more steps to finish. What should the program do?

Show the answer

Have the model summarize the run so far, then continue from that summary. That is compaction: compress what matters, keep going, instead of silently dropping information or letting the run fail.

What happens between sessions 5 min

Monday's session ends. Thursday, the same student messages the assistant again. That is a new session, and the program hands the model a brand-new context window: the instructions, the tools, and Thursday's message. Monday's transcript is not on those pages. The model has no access to anything from Monday unless the program went and put it there.

That's the whole rule: between sessions, the context window does not carry over at all. Each new session starts from nothing. The model does not "remember" an earlier visit, decision or student unless the program retrieves something from outside the context window and places it into this session's pages.

A common mix-up

It's an easy assumption that the assistant automatically remembers every earlier conversation with every student — chat apps often feel that way, and the model is fluent enough each time that it seems like it must recall the last visit. It doesn't. Unless your program saved something to a file or a database during Monday's session and loaded it back in on Thursday, the second session starts exactly as blank as if a stranger had walked in.

What survives, then, is whatever the program deliberately saved outside the context window: a file, a database row, a note. Call that persistent memory: storage that outlives one call and one session, as opposed to the context window, which is temporary scratch space handed to the model and thrown away once the run ends. For your assistant, a student's training status has to live in persistent memory — written once, when training is completed, and read back into context at the start of any later session where it matters.

Check yourself

A student completes laser-cutter training on Monday. On Thursday, in a brand-new session, the assistant correctly tells them they're cleared to use it. What had to be true for that to happen?

Show the answer

Monday's completion was saved outside the context window, and Thursday's session loaded it back in. That save-and-reload step is the only way information crosses a session boundary.

Retrieval: finding the page without pasting the manual 5 min

Say the laser cutter's manual is two hundred pages. If every student question pasted the whole manual into the context window, you would pay for two hundred pages of tokens on every single question, most of them irrelevant to "do I need training first," and the model would have to search through all of it anyway, with context rot working against it the whole time.

The fix is the same idea as Section 3's student record, applied to a bigger store: break the manual into pieces, usually called chunks — a section or a page at a time — and keep them outside the context window. When a question comes in, search the chunks for the ones that best match it, and load only those into context, as a tool result. This is retrieval: finding and pulling in just the relevant piece of a larger store, instead of loading the whole store every time. A system built this way is often called retrieval-augmented, because the model's answer is grounded in the specific passage retrieved rather than in whatever it happened to learn in training (IBM, "What is retrieval-augmented generation (RAG)?").

There are two moments you can retrieve at: load likely-relevant chunks upfront, before the model starts, which is fast but can load things that turn out not to matter; or let the model ask for chunks "just in time," mid-run, through a tool like search_manuals(query), which costs an extra step but only ever loads what the model actually decided it needed. Anthropic describes production agents mixing both, front-loading what's almost always needed and fetching the rest just in time (Anthropic, 2025). Your assistant's search_manuals tool from the agent-loop lesson was already doing just-in-time retrieval, even before you had a name for it.

A common mix-up

It feels natural to picture "giving the model the manual" as literally pasting the manual into the prompt — that is the simplest mental image of handing over knowledge. It's exactly what retrieval avoids. The manual lives outside the context window as files or a search index; only the matching chunk is pulled in for this particular question.

Check yourself

A student asks whether the vinyl cutter needs a special blade for cardstock. Which approach keeps the cost of this one question lowest while still answering correctly from the manual?

Show the answer

Search the manual's chunks for the ones about blades and materials, and load just those. That answers correctly, grounded in the actual manual, for the price of one small chunk instead of two hundred pages.

Notes as memory 4 min

Sections 3 and 4 both end the same way: something useful lives outside the context window, and gets retrieved back in when it's needed. The simplest way to build that "something" is not always a database — it can just be notes. Anthropic calls this structured note-taking: the agent writes short, readable notes to a file as it works, and reads them back later, the way a person keeps a notebook instead of memorizing everything (Anthropic, 2025).

For your assistant, that could be as plain as one small file per student: a line added when training finishes ("Riley: laser cutter training completed, 2026-11-02"), read back at the start of any session where that student's training status matters. No database to stand up before your first design review, nothing exotic to defend — just a file, written and read like any other. Grow into a database later, once a plain file stops being enough; the underlying idea, something persisted outside the context window and retrieved back in, doesn't change.

Worked example and practice 7 min

Worked example: one student, two visits

Monday, Session 1. Riley messages the assistant: "Is the laser cutter free Friday, and do I need training?"

  1. Call 1's context window: instructions + Riley's question. The model requests check_calendar(laser_cutter, friday). This is still just one call's pages; nothing has been saved anywhere yet.
  2. Call 2's context window: everything from call 1, plus the calendar result. The model requests search_manuals("laser cutter training requirement") — retrieval: only the matching chunk of the manual comes back, not the whole manual.
  3. Call 3's context window: everything so far, plus that chunk. The model writes its final answer: Friday is free, and training is required first. The program also calls update_student_record(riley, "laser_cutter_training: not completed") — a write to persistent memory, separate from anything in the context window.
  4. Session 1 ends. Its whole context window — three calls' worth of pages — is discarded. Only the record file survives.
  5. Riley completes training that afternoon. The program writes again: update_student_record(riley, "laser_cutter_training: completed 2026-11-02").

Thursday, Session 2. Riley messages again: "Can I use the laser cutter today?" This is a brand-new context window: instructions + this new question, nothing from Monday. The model requests check_training_record(riley) — retrieval of one row, not the whole roster — and gets back "laser_cutter_training: completed 2026-11-02." With that in its context window now, it answers: yes, Riley is cleared. Riley never has to repeat what they already proved on Monday, and the model never had to "remember" Monday at all — it only had to retrieve one saved fact.

Show a solution
  1. Call 2's context window holds everything from call 1, plus the retrieved manual chunk saying training is required. The model likely requests check_calendar(3d_printer, ...) next to find an open slot, or asks Jordan which day they want, depending on how the tool is designed.

Summary 2 min

  • The context window is everything handed to the model for one call; within a session it only grows, call after call, until compaction or the end of the run.
  • Between sessions, the context window does not carry over at all — a new session starts empty, and the model "remembers" nothing unless the program retrieves it from somewhere else.
  • Persistent memory is storage outside the context window — a file, a database row, a note — that outlives a session and can be read back into a later one.
  • Retrieval is the search step that finds just the relevant piece of a larger store, whether that store is a 200-page manual or a folder of student records, so you never have to paste the whole thing into every prompt.

Say it in your own words: without looking back up, explain to yourself why a brand-new session on Thursday can still correctly tell Riley they're cleared to use the laser cutter, even though the model has no memory of Monday's conversation.
