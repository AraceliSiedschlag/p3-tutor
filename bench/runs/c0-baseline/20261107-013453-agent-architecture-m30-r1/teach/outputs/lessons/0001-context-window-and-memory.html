Context and memory in an agent

By the end of this lesson you can say exactly what your makerspace assistant sees on any given call, what survives from one step to the next within a run, what survives between separate sessions (by default, nothing), and how notes and retrieval let you design around that on purpose.

Objective O3: the context window, what's kept between steps and sessions, and retrieval and notes as memory About 30 minutes Builds on the agent loop
Why this matters for you

Your assistant has to answer from machine manuals that run to dozens of pages and remember whether a student finished laser-cutter training — weeks after they did it. Both of those are context and memory problems, not model problems. Get the architecture right here and you can defend it at your design review; get it wrong and your sponsor's model budget disappears into re-reading the same manual on every question.

It sends the result back to the model as part of the model's next input, and calls the model again, so the model can use that result to decide its next step or write its final answer. That's the piece this lesson builds on: "the model's next input" is exactly what the context window holds, and today you'll look at what else is in there, what stays, and what doesn't.

The context window 6 min

Every time your assistant's model is called, it is handed a single block of text: the system prompt, the descriptions of every tool it can use, the whole conversation so far, and any files or tool results included in it. That whole block is the context, and the most it can ever be — the model's limit on how much it can take in at once, counting what it writes back too — is the context window (Claude Platform Docs, "Context windows"). Anthropic's own engineers describe context more simply still: it's "the set of tokens included when sampling from a large-language model" ("Effective context engineering for AI agents," Anthropic).

A token is the unit that gets measured and billed: a chunk of text, on average a bit less than a word — roughly 3.5 English characters (Claude Platform Docs). Current Claude models have context windows up to 1 million tokens, which is around 750,000 words — a lot, but still a hard ceiling, and every token in that window is one you pay for, whether it is the system prompt, a tool's description, a manual page, or the model's own answer. This is the lever behind your sponsor's "cost per request matters": a request that stuffs 20,000 tokens of manual into context costs roughly 20 times what a request with 1,000 relevant tokens costs, every single time a student asks a question.

Within one run of the loop, the window only grows. Each step's tool result is appended to everything before it, and the next model call sees the lot: the Claude docs call this "progressive token accumulation" — each turn's input is the full history plus the new result, and previous turns are kept completely (Claude Platform Docs).

This is also why a long-running agent can stall: if every step's input keeps growing and nothing is summarized or cleared, the window eventually fills up, and cost climbs with it — which is one reason the step limit from your last lesson matters for budget, not just correctness.

Between sessions: nothing, by default 6 min

Section 1 was about one run of the loop, start to finish, answering one request. But a session ends: your assistant gives its answer, the student walks away, and at some point a completely separate run starts, maybe for the same student days later. What carries over from the first run into the second?

By default: nothing at all. Each call to the model is a fresh request with its own context window, built from whatever your program puts into it this time. If your program doesn't put Monday's conversation in, the model on Thursday has never seen it — not a summary, not a trace, nothing. The model itself holds no notebook between calls; it only ever reacts to what's in front of it right now.

A common mix-up

It's tempting to think the model remembers students, or tool choices, or past conversations on its own, especially once you've chatted with one for a while and it feels continuous. That feeling comes entirely from the program resending the transcript every turn — the model itself never retains anything once a call finishes. Across separate sessions, with no transcript resent, there is no continuity at all unless your program explicitly builds it: reads something it saved, and puts it back into this session's context. "The assistant remembers Mo from last week" is a sentence about your database, not about the model.

This matters for your design review, because it means memory is not a model feature you get by choosing a bigger model — it is something your program has to build, deliberately, on top of a model that forgets everything the instant a run ends.

Notes as memory 6 min

If the model forgets everything by default, "memory" can only mean one thing in practice: your program writes the fact you need later to somewhere that outlives the session — a file, a database row, a row in a spreadsheet — and reads it back into context the next time it's relevant. Anthropic's engineers call this structured note-taking: agents "periodically write notes... that persist outside the context window," then pull the relevant note back in later ("Effective context engineering for AI agents"). Their own example is an agent playing a long video game across thousands of steps: it keeps a map of what it's explored and a note of which achievements it has already unlocked, and after its context is cleared, it reads its own notes back and keeps going as if nothing had been lost.

For your assistant, the fact worth that treatment is exactly the one your mission names: whether a student has completed training on a given machine. The design is simple once you see it this way — it has nothing to do with the model's context window size, and everything to do with where the fact of record lives:

A common mix-up

It's easy to think the fix for "the model forgets" is simply a model with a bigger context window — if it could hold more, surely it could hold on to more. But a bigger window is still only ever filled fresh at the start of each call; it doesn't change what happens between sessions at all, and a window big enough to hold every student's whole history would be enormous and expensive to pay for on every single question, most of it irrelevant to whoever is asking. The fix is not a bigger window; it's a persistent record outside any window, read back only when it's actually needed.

Notice the shape of this: writing is rare and deliberate (a note gets written when something worth keeping happens), while reading is targeted (only the one record relevant to this student and this machine comes back into context, not every student's whole file). That asymmetry is what keeps memory cheap even though context is expensive.

Retrieval for long reference material 6 min

Training records are small, one fact per student per machine. Your machine manuals are not: forty pages for the laser cutter alone. The same logic from Section 3 still applies, but now the record you're pulling from is huge, and the question is which slice of it belongs in context for this one question.

The wrong instinct is to play it safe by loading the whole manual into every call, reasoning that more information can only help. It doesn't: tokens cost money whether the model uses them or not, and performance actually gets worse as context grows, a pattern researchers call context rot — "as token count grows, accuracy and recall degrade" (Claude Platform Docs). Anthropic's engineering team put the design goal plainly: "finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome" ("Effective context engineering for AI agents"). Thirty-nine pages of irrelevant manual, sitting in context next to the one sentence that answers the question, is exactly the opposite of that.

The fix is retrieval: instead of pre-loading the whole document, the program keeps the manual outside context, and the model asks for the relevant piece only when it needs it — by calling a tool like search_manuals(machine, topic), which your assistant already has. Anthropic compares this to how people handle any body of knowledge too big to memorize: "we generally don't memorize entire corpuses of information, but rather introduce external organization and indexing systems like file systems, inboxes, and bookmarks to retrieve relevant information on demand" ("Effective context engineering for AI agents"). You don't memorize the maintenance manual for your car; you keep it in the glovebox and open it to the right page when the warning light comes on. search_manuals is your assistant's glovebox.

A common mix-up

"Load everything, just in case" feels thorough and safe — missing a detail seems worse than including too much. In fact the opposite is true: including too much makes the one relevant detail harder for the model to find and weigh correctly, on top of costing more every time. A targeted retrieval that returns the one right passage is usually both cheaper and more accurate than a wall of mostly-irrelevant text.

Retrieval and notes solve different problems, even though both keep things out of context until needed. Notes are for facts your own program created (a training completion, a booking); retrieval is for reference material that already existed before your assistant ever ran (the manuals). Both share the same rule: keep it outside context, bring back only what this call needs.

Worked example and practice 8 min

Worked example

Mo asks your assistant on Monday, "Can I use the laser cutter?" Mo asks again on Thursday, in a brand-new session. Trace what the assistant keeps, and what it has to look up again.

  1. Monday, call 1: context holds the system prompt, tool definitions, and Mo's question. The model calls check_training_record(Mo, laser_cutter), which comes back "not completed." That result is added to context for call 2.
  2. Monday, call 2: with the training result now in context, the model tells Mo to complete the training module and points to it via search_manuals. Monday's session ends; this whole context window is discarded.
  3. Between sessions: Mo actually completes the training (through some other part of the system, not this chat). Your program writes one row to the training database: Mo, laser cutter, completed, 2026-11-03. This write is the only thing that survives Monday — not the conversation, the fact.
  4. Thursday, call 1: a brand-new context window, with no trace of Monday's chat. Mo asks the same question. The model calls check_training_record(Mo, laser_cutter) again — it has to; it doesn't remember Monday's answer — and this time the database returns "completed."
  5. Thursday, call 2: with that fresh result in context, the model tells Mo they're cleared to use the laser cutter. The model never "remembered" anything across the two days; your database did, and the tool call fetched exactly the one fact needed, right when it was needed.

Summary 2 min

  • The context window is everything the model sees on one call: system prompt, tools, conversation so far, and tool results — measured and billed in tokens.
  • Within one run, context only grows: every step's result is added to what came before, and nothing is dropped automatically.
  • Between separate sessions, by default nothing carries over at all — the model has no memory of its own; any continuity has to be built by your program.
  • Memory, in practice, means writing a fact to a persistent record outside any context window, and reading just that record back in when it's next relevant — not a bigger window.
  • For reference material too big to preload, retrieval does the same job: keep it outside context, fetch only the relevant slice through a tool call, just in time.
