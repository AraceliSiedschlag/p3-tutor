Context and memory: what your agent sees, and what it keeps

By the end of this lesson you can decide, for any request to your makerspace assistant, exactly what the model reads on one call, what disappears the moment that call ends, and what has to be written down somewhere else so it survives until the student's next visit.

Objective O3: context, memory, and retrieval About 30 minutes Builds on the agent loop you already traced
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits, on a small model budget. Both of those are context-and-memory problems. Get this wrong and the assistant either forgets everything useful or pastes whole manuals into every call and burns through the budget. Get it right, and you can defend the design at your review.

Warm-up 2 min

Recall

In the agent loop, the model asks to call check_calendar(machine, date). The program runs it and gets back a result. What happens to that result next, and who sees it?

Check your answer

The program hands the result back to the model as part of its next input, and the model is called again with that result in front of it. Nothing about this is automatic memory: the program has to explicitly put the result where the model will read it. That "where the model will read it" is today's topic.

The context window 6 min

Picture the fourth call in your assistant's loop: the student asked about the laser cutter, the model has already called check_calendar and search_manuals, and now it is about to write its final answer. What does the model actually have in front of it for that one call? Not a database connection, not "the conversation" as an abstract thing — a single block of plain text, assembled by your program, containing the system instructions, the list of tools and what they do, the student's question, and both tool results so far, all concatenated together.

That whole block is called the context window: all the text a model can reference when generating one response, including the response itself. Anthropic's own documentation calls it the model's "working memory" for that single call, as opposed to the vast training data the model learned from once and never sees again (Claude docs, Context windows). The window is measured in tokens, the small chunks of text — pieces of words, punctuation, whitespace — that the model actually reads and writes one at a time, which is also how most providers price a call: you pay for however many tokens went in and came out.

Every model has a hard cap on tokens per call. Make the block above the cap — instructions, tools, question, every tool result, stacked up — and the call simply fails or gets cut off. Stay under the cap but still make the block very large, and something subtler goes wrong: accuracy and recall quietly degrade as token count rises, a pattern Anthropic calls context rot. "More context isn't automatically better" is the exact line from their documentation (Claude docs, Context windows); a model's attention is a limited resource, much like a person's working memory, and it gets spread thinner the more you pile in (Anthropic, Effective context engineering for AI agents).

Picture two designs for the same laser-cutter question. One keeps the block lean: a short system prompt, two tool calls, two short results. The other pastes the entire thirty-page safety manual into every call, "just in case" it is needed. Both might land on the same correct answer today. But the second design pays for those thirty pages of tokens on this question, and on the next student's question, and the one after that — every call, for as long as the assistant runs — while the first pays only for the handful of lines that were actually relevant. On the small, sponsor-funded budget your mission runs on, that gap compounds fast across a semester of student questions.

Everything in the request counts toward the window, including things you might not think of as "the conversation": the tool definitions themselves, any images or documents attached, and your system instructions. A long list of elaborately described tools quietly eats the same budget as a long conversation does.
A common mix-up

"A bigger context window means the assistant remembers more." It is tempting because both ideas sound like "holds more." But window size only changes how much text can fit into one call right now. It says nothing about whether any of that text is still around for the next call, let alone next week. A model with a huge window and no plan for what to keep is not more forgetful or less forgetful than a small one — it is just as blank at the start of a new session either way. Size and persistence are two separate questions, and the rest of this lesson is about the second one.

The tool result is right. The window is exactly the text your program assembles for that one call: instructions, tools, the question, and anything that has already come back from a tool — nothing more, nothing the model "already knows" from training, and nothing sitting unread on disk.

What a loop keeps between steps 4 min

You already know the agent loop repeats: the model asks for an action, the program runs it, the result goes back in, and this continues until the model is done. Figure 1 shows the part that matters now — by default, nothing is thrown away between those steps. Step 2's call includes everything from step 1 plus the new result; step 3's call includes everything from steps 1 and 2 plus its new result, and so on. The context window only grows within a single run, never shrinks on its own.

Recall the coding agent stuck making the same failing edit for 40 steps. All 40 steps were still sitting in its context: that is exactly why the fix was not a bigger window, it was a stopping condition. A long-running loop keeps paying the token cost of its entire history on every single step, and once that history is long enough, context rot means the model is also reasoning worse with each step, not better. Anthropic's engineers describe this directly: an agent's own actions "generate increasingly large amounts of context... that must be cyclically refined as the task progresses" (Anthropic, Effective context engineering for AI agents). Deciding what to keep, trim, or summarize mid-run is a real design problem, not a detail you can ignore until it is expensive.

Put a number on it. Say a lean system prompt and tool list run to 400 tokens, and each tool result that comes back adds another 300. Call 1 reads 400 tokens. Call 2 reads 700 (400 plus the first result). By call 4, the model is reading 1,300 tokens of input before it writes a word of its answer — and every one of those 1,300 tokens is billed again in full, because none of the earlier ones were ever removed. A run that drags on for dozens of steps, like the stuck coding agent, can turn a few-hundred-token question into a bill many times the size, for an answer that is no better, and possibly worse.

Hold onto one distinction before moving on: everything in this section happens while a run is still going — the same conversation, the same thread of tool calls. The next section is about what happens once that run ends.

What survives between sessions 5 min

Suppose the student from this morning comes back tomorrow with a follow-up question. Your program starts a new call. What is in its context window this time?

By default: nothing from yesterday. A fresh call starts with only the fixed system instructions and tool list; the question-and-answer text from yesterday's run is gone unless your program went and put it back. Calls to a model are stateless on their own — the model does not sit there between calls holding anything in reserve. Whatever continuity you want across sessions has to be built by you, outside the window, and loaded back in at the start of the next one.

A common mix-up

"The assistant automatically remembers earlier conversations." It is an easy thing to assume, because talking with an assistant feels continuous, the way talking with a person does. But a person's memory keeps working between sentences without anyone doing anything; a model call does not. If yesterday's training note is available tomorrow, it is because your program wrote it to a file or database yesterday and read that file back in today — two deliberate steps, not one invisible one. Skip either step and the assistant genuinely does not know the student walked in before.

This is what memory means for an agent: not something the model does, but a design decision in the program around it — write the fact down somewhere durable the moment it becomes true, and read it back into context at the start of whichever later call needs it. "Did this student complete laser cutter training, and when?" is exactly this kind of fact: cheap to store, worth keeping past the session that created it.

Retrieval: searching instead of carrying 5 min

A training record is small: one date, one machine, done. A machine manual is not — forty pages the context window could not hold in full even once, let alone on every call, and even if it fit, context rot means stuffing all of it in would make the model's reasoning worse, not safer, while costing you tokens on every single question regardless of whether that question needed page 3 or page 31.

The fix is the same shape as a tool call you already understand: instead of handing the model the whole manual, give it a tool — call it search_manuals(query) — that searches a pre-built index of the manuals and returns just the few paragraphs that actually match the question. This pattern has a name, retrieval-augmented generation (RAG): a system searches a collection of documents for the passages relevant to a question, then hands only those passages to the model, so it answers from the retrieved text rather than needing it all along (AWS Prescriptive Guidance, Understanding Retrieval Augmented Generation). The model never sees the other thirty-nine pages; it sees a short result, structurally identical to a check_calendar result, just produced by a search instead of a calendar lookup.

Building that search tool takes some work up front: breaking each manual into smaller chunks, a paragraph or a short section at a time, and building an index that can quickly find the chunks whose words or meaning match a question, so search_manuals can hand back two or three chunks instead of the other hundred. That indexing work is paid once, when the manuals are loaded in; every question afterward stays cheap, because the model only ever reads a few hundred tokens of manual text instead of tens of thousands.

Anthropic's engineers call this a "just-in-time" strategy: keep a lightweight pointer to where information lives, and load the actual content only at the moment a step needs it, instead of pre-loading everything a task might ever touch (Anthropic, Effective context engineering for AI agents). Section 1's mix-up shows up again here in a new costume: "paste the whole manual to be safe" feels thorough, but it is the same error as "a bigger window means more memory" — it burns budget and accuracy on text the question never asked about.

Search the manuals. A fixed spec in a manual is retrieved, not remembered or looked up in a student record; nobody wrote it down specially for this student, and the model never learned your shop's manuals during training.

Notes as memory 4 min

Retrieval searches something that already existed in bulk before the question was asked — the manual was written long ago. But some of what an agent needs to remember is not sitting in any document; it is a fact the agent itself discovers or produces along the way, like "this student finished laser cutter training on November 6th." For facts like that, Anthropic's engineers describe a second pattern: structured note-taking, where the agent "regularly writes notes persisted to memory outside of the context window," which then "get pulled back into the context window at later times" (Anthropic, Effective context engineering for AI agents). Their own examples include a coding agent's running to-do list and a long-running game-playing agent that keeps tallies and maps of what it has already explored — small, authored facts, not a search index.

For your assistant, this means a short record per student: training completed, which machine, which date, written the moment it happens and loaded back in whenever that student's name comes up again. Retrieval and notes are both "memory outside the window," but they differ in origin: retrieval searches a large pre-existing source you did not write; notes are small facts your own program writes as it goes, specifically because they are worth the (small) cost of storing and reloading. Deciding which facts earn that status — and which are fine to just re-derive or re-ask each time — is a real design call, and it is the one your mission asks you to be able to make.

Not every fact earns a note. The spacing around an exhaust vent never changes from one student to the next, so there is no student-specific fact to write down — it stays a retrieval, searched fresh whenever anyone asks. A note is for something true about one particular student, project, or piece of equipment, discovered at a moment that will not come back around on its own, like the exact day training happened. Writing a note for everything else just rebuilds the whole-manual problem from Section 4, one small file at a time — except now you also have to keep every note correct as policies change, instead of letting one well-maintained manual stay the single source of truth.

Notice the asymmetry: a note is cheap because it is short (one date, one machine), so reloading it costs almost nothing. The failure mode to avoid is treating "memory" as license to save everything.

Worked example and practice 6 min

Worked example

"Can I use the laser cutter? I trained eight months ago." Trace what the assistant does, call by call.

  1. Call 1: the model reads the system prompt, tool list, and the question — nothing else yet — and decides it needs the student's training history. It requests check_training_record(student_id).
  2. The program runs that tool. This is a memory lookup: it reads a record the program itself wrote the day training happened, not a document search. It returns: laser cutter, completed eight months ago.
  3. Call 2: the model's context now also holds that result. It still does not know the shop's renewal rule, so it requests search_manuals("laser cutter training renewal period").
  4. The program runs that tool. This is retrieval: a search over the manual's existing text, returning just the matching paragraph — say, "retrain every six months." Not the whole manual, and nothing was saved specially for this student.
  5. Call 3: the context now holds both results on top of the original question. Eight months is past six, so the model writes the final answer: no, retraining is required first.
  6. Session ends. The context window built across these three calls is discarded entirely. Nothing about today's chat survives — only the training record, already saved from eight months ago, is still sitting outside the window, ready for next time.

Notice that only one of those six steps touches anything written specifically for this student. The manual search would return the exact same six-month rule for any student who asked; the training lookup is the only place this particular person's history shows up at all.

Your turn

A different student asks: "Do I need a new orientation? It's been seven months since my 3D printer training. Also, what's the rule for leaving a print running overnight?" Step 1 is given: the model requests check_training_record(student_id), a memory lookup, since the training date is a fact your program saved itself. Work out the rest: what does the model still need, where does each piece come from (memory or retrieval), and what happens to all of it once this session ends?

Show a solution

Next, the model needs the renewal rule for 3D printer training, which is fixed text in the manual — a search_manuals call, i.e. retrieval, not a lookup tied to this student. Separately, the overnight-printing rule is also fixed shop policy written in a manual, so that is a second retrieval call, unrelated to any student record. With all three results now in context — the training date, the renewal rule, and the overnight rule — the model can compare seven months against the renewal period and answer both parts at once. When the session ends, this entire context window is thrown away; only the training record (already saved before this conversation began) remains for next time. Nothing about tonight's overnight-printing question needs to be remembered afterward, because it was never a fact about a specific student — it was always sitting in the manual, available to retrieve again whenever anyone asks.

Summary 2 min

  • The context window is the one block of text a model reads for a single call — instructions, tools, question, and results so far — measured in tokens, bounded, and paid for on every call.
  • Within one run, the loop keeps everything from earlier steps by default; the window only grows, so long runs get both more expensive and, past a point, less accurate (context rot).
  • Between sessions, nothing survives by default. Continuity exists only where your program deliberately wrote something down and deliberately loads it back in.
  • Retrieval searches a large, pre-existing source (a manual) for just the relevant passage, instead of carrying the whole thing in every call.
  • Notes are small facts your own program authors as they happen (a training date) and reloads later — memory you build, not something the model does on its own.

Say it in your own words: explain to a teammate why telling the model "please remember this for next time" in a prompt would not work, and what you would build instead so the assistant reliably remembers a student's training date.
