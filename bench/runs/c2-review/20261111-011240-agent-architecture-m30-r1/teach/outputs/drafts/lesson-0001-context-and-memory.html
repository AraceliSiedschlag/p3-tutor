Context and memory: what your agent actually remembers

By the end of this lesson you can decide, for any fact your makerspace assistant needs, whether it belongs in the live context, gets retrieved from the manuals on the spot, or gets saved as a note for next time — and explain why "the model will just remember" is never a safe plan.

Objective O3: the context window, what persists and what doesn't, and memory by design About 30 minutes Builds on the agent loop you already know
Why this matters for you

Your makerspace assistant has to answer from long machine manuals and remember each student's training status between visits. Both of those are memory problems, and both break if you assume the model "just knows" things it was never actually given.

There's a budget angle too: every extra token you stuff into context is a token you pay for, on every single call. Get this lesson right, and you're not just avoiding a bug — you're protecting the sponsor's budget.

Warm-up 2 min

Recall

You already know two things that today's lesson sits on top of. First: what does a language model actually know, according to the first lesson you did? Second: in the agent loop, what happens to a tool's result right after the program runs the tool?

Check your answer

A model knows only what it learned in training, plus whatever text it's given as input — nothing else exists for it. And in the agent loop, a tool's result gets sent back to the model as part of its next input, so the model can use it to decide what to do next.

Put those two together and you've basically already got today's whole lesson in your pocket: everything the model "knows" during a run is just text that got put in front of it, and that text is called its context.

The context window 5 min

A context window is all the text a model can reference when it generates a response in one call — your system prompt, the whole conversation so far, any tool results, your tool definitions, and the model's own output, all added up and measured in tokens, roughly word-sized chunks of text (Claude Platform Docs, "Context windows"). That page calls it a "working memory" for the model, and that's the right picture: not a filing cabinet it can dip into later, just what's on the desk in front of it right now.

If you've built anything with a web server, this will feel familiar: a server handles each HTTP request on its own and keeps nothing from the last one unless you explicitly stored it somewhere — a cookie, a session table, a database row — and read it back in on the next request. A model call works exactly the same way: there is no hidden state sitting inside the model between calls.

That's true even inside what looks like one continuous chat. Ask a question, get an answer, then type a follow-up right below it in the same window: the model doesn't privately remember your first question. The chat app resends the entire conversation so far, every time, as part of the next call's input. If a fact isn't sitting in the text you send this time, it does not exist for the model this time, full stop.

Check yourself

You ask your makerspace assistant a question in a chat window, it answers, and you type a follow-up question right below it in the same window. Why does the model's answer to your follow-up take your first question into account?

Show the answer

The chat app resends the whole conversation so far, every time. Nothing is held inside the model itself between calls.

Context grows every step 7 min

Inside one agent run, the context doesn't just get resent — it accumulates. Call 2 doesn't only see the newest message; it sees the system prompt, the first message, the model's first move, the tool result, and the newest message, all over again, because the program has to hand the model its whole history each time. Call 3 carries all of that plus whatever call 2 added. The pile only grows.

Put rough numbers on it, since your sponsor's budget is real. Say your assistant answers "Can I use the CNC router today?" with one calendar check:

  • Call 1 sends about 600 tokens: your system prompt plus the student's question.
  • The calendar check's result joins the context, so call 2 sends about 750 tokens.
  • A manual search's result joins next, so call 3 — the one that finally writes the answer — sends about 1,150 tokens.

Three calls, and you're billed for the input tokens on every one of them, not just the last. A run that quietly grows to ten tool calls before answering doesn't cost ten times one call — it costs the sum of ten growing piles, which adds up fast.

This is also why a step limit matters — the safeguard you already learned for a stuck agent: every extra step adds a whole copy of the growing history to every future call's cost.
A common mix-up

It's tempting to think a bigger context window is just better, since the model can "see more." But real conversation history is preserved completely and resent every turn (Claude Platform Docs).

And performance actually degrades as token count grows, a pattern Anthropic calls context rot (Anthropic, "Effective context engineering"). More isn't free, and it isn't automatically better: every token in context costs money at every call, and a context stuffed with half-relevant material makes it harder, not easier, for the model to find the part that matters. The skill isn't maximizing what's in context — it's curating it.

Check yourself

Your makerspace assistant is two tool calls into one run: it called check_calendar, then search_manuals, and now it's about to make its third model call to write the final answer. What does that third call send to the model?

Show the answer

The full accumulated history, including both tool results. The model has no state of its own between calls — the program must put everything relevant back in front of it, every time.

Steps vs. sessions 6 min

So within one run, context grows and carries forward automatically, because the program keeps resending it. But a run ends — the student gets their answer and closes the chat, or the loop hits its final answer. What happens to all that accumulated text then?

It's thrown away. Unless your program deliberately writes something to a file or a database before the session ends, that whole transcript, and everything the model worked out during it, is gone — the same statelessness you just saw within one call, now at the scale of an entire conversation. As Anthropic's memory tool docs put it plainly, memory "lives entirely in your application," not in the model (Claude Platform Docs, "Memory tool").

The next session — the same student, back next week — starts from nothing: a fresh system prompt, no tool results, no memory of last week's conversation. The model that answers next week's question is, as far as its input is concerned, meeting this student for the first time.

A common mix-up

This is the one to watch for yourself on: it's natural to assume an assistant "just remembers" a student from a past visit, the way a person who worked the front desk last week would. A model doesn't.

There is no built-in, automatic memory of earlier conversations — that's exactly the wrong option from quiz 0001, q1, not within the same provider, not for the "same" chat window reopened later, not ever, unless a program explicitly saved something and fed it back in as text. If your assistant seems to remember a regular student, it's because someone built a note-saving step, not because the model is quietly keeping tabs on anyone.

Check yourself

Last Tuesday, a student finished laser-cutter safety training through a chat with your assistant. Today, that same student opens a brand-new chat and asks to book the laser cutter. Your program saved nothing from Tuesday's conversation anywhere. What does today's first model call know about Tuesday?

Show the answer

Nothing. With nothing saved on Tuesday, there is no text anywhere in today's input that mentions the training, so today's model call has no way to know about it.

Retrieval: searching a big reference 5 min

If nothing persists on its own, "memory" is really just a design decision: what do you deliberately save, and how do you bring it back? For your assistant, there are two different problems hiding under that one word. Here's the first.

Your machine manuals might run hundreds of pages. You can't put all of them in context every call: too many tokens, too much cost, and context rot makes the model worse at finding the one paragraph that matters anyway. The fix is retrieval: instead of loading everything up front, you search the manuals for just the few passages relevant to this question, and load only those into context, on demand (Anthropic, "Effective context engineering").

If you've worked with a database, this is a familiar move. A query that returns the top few matching rows instead of dumping the whole table does the same job: keep a lightweight way to find things (an index, a search tool), and pull in only the specific record you need, when you need it.

Check yourself

A student asks what the maximum bit size is for the drill press — a fact stated once, in one line, somewhere in the 80-page drill press manual. What should the assistant's program do?

Show the answer

Search the manual for the relevant passage and load only that into context. The fact is one line in a large static reference, which is exactly what retrieval is for.

Notes: memory you build on purpose 5 min

Here's the second problem. A student's training record isn't "in" any manual — it's specific to that person. And it needs to still be true next week, which retrieval over a static document can't give you, because nothing about it is static.

What you want instead is structured note-taking, sometimes called agentic memory. The program (or the model, told to) writes a short note to a file or database. That note — not the whole conversation it came from — gets loaded back into context the next time it's relevant (Anthropic, "Effective context engineering").

Anthropic's own memory tool works exactly this way: the model checks a small directory of notes before starting, and writes updates to it as it learns things. A later session can pick up where an earlier one left off without replaying everything that was said (Claude Platform Docs, "Memory tool").

Since you cook: think of it the way a kitchen runs a prep list. The next cook on shift doesn't re-read every order ticket from yesterday to know the stock reduction is already done. Someone wrote "stock reduced, in the walk-in, use by Thursday" on a card. That card is the note — small, specific, and exactly enough to pick up where the last shift left off. Nothing more.

A common mix-up

Don't reach for retrieval when what you actually need is a note, or the other way around. Retrieval answers "where, in a large existing reference, is the information for this question?" A note answers "what did we learn or decide that needs to still be true later?"

Searching the manual every time for a student's personal training status won't work, because that fact isn't written in any manual. And saving a note for every paragraph of every manual would be pointless duplication of something that's already sitting there, searchable, whenever you need it.

Check yourself

Your assistant needs two things to answer "Can I use the 3D printer, and what filament is a first-timer allowed?": (1) the shop's filament rules for first-timers, written in the equipment manual, and (2) whether this specific student has used the 3D printer before. Which is the better fit for retrieval, and which for a saved note?

Show the answer

Retrieval for the filament rule (search the manual, load the one relevant passage); a saved note for the student's personal history (a small, per-student fact that must survive until their next visit).

Worked example and practice 6 min

Worked example

A student opens a new chat and asks: "Can I use the CNC router today, and did you tell me last month I needed extra training for it?" Walk through what the assistant's program should do, call by call.

  1. Before anything else, load the saved note for this student, if one exists — something like "Riley: shop safety done Sept 2; CNC router training: not yet recorded." This is memory by design: a small fact, written on purpose weeks ago, read back in at the start of a brand-new session, exactly like Figure 2. Without this step, the assistant would greet a regular like a stranger every single visit.
  2. Call 1: the model requests check_calendar(CNC router, today) to answer the booking half of the question. The result comes back and joins the context for the next call — this part is the ordinary agent loop, carrying forward within the run, like Figure 1. It costs tokens, but it's a small, one-time addition, not a growing archive.
  3. Call 2: the model requests a retrieval search over the manuals for "CNC router extra training requirement," since that's a fact buried in a long static document, not something to guess or store per student. The search returns one short passage, which joins the context too, instead of the whole manual.
  4. Call 3: with the note, the calendar result, and the retrieved passage all now in context, the model writes the final answer. Everything it needed was either loaded on purpose (the note), fetched on demand (retrieval), or carried forward within this run (the tool result) — nothing was simply assumed to be "remembered."
  5. Before the session ends, the program updates the saved note if anything changed — say, the student just completed the extra training during this chat. That's the only thing that survives to next time; the rest of this transcript is discarded, as in Figure 2.

First step given: the program loads this student's saved note, if any exists. What happens next, call by call, and what (if anything) gets saved when the session ends?

Show a solution

Call 1: the model requests check_calendar(3D printer, this afternoon); the result joins the context for the next call, same as any tool result within a run. Call 2: the model requests a retrieval search over the manuals for "first-timer filament rules," since that's a fact in a large static document; the one relevant passage is loaded in. Call 3: with the note (if the student had one), the calendar result, and the retrieved passage all in context, the model answers.

At the end of the session, the program updates the student's note only if something changed that needs to persist — for instance, recording that this was their first 3D-printer session, so a future visit knows they're no longer a first-timer. The filament rule itself never gets saved as a note; it stays in the manual, where retrieval can find it again whenever anyone needs it.

Summary 2 min

  • The context window is all the text sent into one model call — system prompt, history, tool results, tool definitions — measured in tokens. The model has no state of its own outside it.
  • Within one run, context accumulates automatically: the program resends the growing history every call. Across sessions, nothing persists automatically: the transcript is discarded unless something was deliberately saved.
  • "The model will remember" is never a safe assumption — not within a run past what's been resent, and never across sessions without an explicit save-and-reload step.
  • Retrieval handles a large, mostly-static reference: search it, load only the relevant passage, on demand.
  • Notes handle a small fact that must survive to the next session: write it deliberately, load it back in at the start.

That's genuinely most of a memory architecture for a real system — a lot of people building their first agent skip straight to "it'll just remember" and get burned by it later. You won't.
