Context and memory: what the assistant remembers, and how

By the end of this lesson you can take any moment in the makerspace assistant's agent loop and say, correctly, what is currently sitting in its context window, what will and will not still be there next session, and whether retrieval or notes is the right fix for getting old information back.

Objective O3: the context window, what's kept between steps and sessions, and retrieval and notes as memory About 30 minutes Builds on the agent loop
Why this matters for you

Your makerspace assistant has to answer questions out of machine manuals that run hundreds of pages, and it has to remember which students have finished laser safety training across weeks of visits. Both of those are context-and-memory problems: what the model can actually see right now, and what the surrounding system can still dig back up later. Get this wrong in your design and the assistant either forgets everything or costs far more per request than it needs to — get it right, and you can defend the design at your review.

Check your answer

Because what the model knows comes only from patterns learned in training, plus whatever text it's given right now — it has no way to check whether a fact is still true, so it produces plausible text either way. That same idea, that the model only knows what's in front of it, is the floor for everything in today's lesson: what's "in front of it" at any moment is exactly what the context window holds.

The context window: finite, token-counted working memory 4 min

Everything the model reads or writes is measured in tokens: a token is a chunk of text, roughly three-quarters of a word. Every token sent to the model, and every token it sends back, is counted against a size limit, and against what the call costs (Redis, LLM context windows). A long manual, a long conversation, a long tool result — they all eat the same token budget.

Every single time the model is called, it sees exactly one thing built from those tokens: its context window, the full set of tokens it can attend to in that one call. It includes the system prompt (the instructions that set up the model's role and task), the tool definitions (a short description of each tool the model is allowed to call and what it needs to call it), the back-and-forth conversation so far, every tool result that's come back, and whatever the model is writing right now (Anthropic, Effective context engineering for AI agents). People often call it the model's "attention budget," and like any budget, it's finite — it doesn't grow to fit whatever you throw at it.

That matters a lot for your assistant. The makerspace manuals run hundreds of pages. No matter how generous the context window is, the system prompt, the tool definitions, the conversation so far, and any manual text you pull in all have to share that one limited space — nothing here gets its own separate pile of room.

Context windows have grown enormous — some models now take in hundreds of thousands, even a few million tokens (Redis, LLM context windows). Still finite, though, and as Section 4 will show, fitting isn't the only cost that matters.

Picture prepping a big, multi-dish dinner on one counter with one cutting board. You don't get to spread the entire cookbook open while you cook — only what's laid out in front of you right now gets used, and pile on too much and there's no room left to actually work. The makerspace manual is the cookbook: far too long to lay out whole, so only a slice of it can sit in the model's workspace at a time.

Check yourself

The assistant's context window holds up to 200,000 tokens. So far this call has used 4,000: the system prompt, tool definitions, and one short calendar result. A tool result just came back with the entire 300-page manual in it — about 90,000 tokens — and it was appended to the conversation. Is that manual text inside the context window right now, and why?

Show the answer

Yes, it's in the window: 94,000 tokens used out of 200,000 available, and nothing has removed it. But "it technically fits" and "it's free to include" are two different claims — size and cost are not the same thing, which is exactly where Section 4 picks up.

Within one session: the loop keeps feeding the growing context back in 4 min

Remember the agent loop from learning record 0002: the model asks for an action, the program runs it, the result comes back, and this repeats. Here's the part that wasn't said out loud yet: every step's tool call and tool result get appended to the context, and that whole, growing transcript is what gets sent back to the model on the very next call (Anthropic, Effective context engineering for AI agents). That's what "kept between steps" actually means — nothing is thrown away mid-loop by default.

So the context doesn't reset between steps; it grows. Step 2's call sees step 1's result still sitting there. Step 5's call sees everything from steps 1 through 4, plus its own new material. That's also why a long-running loop eventually needs trimming — more on that fix in Section 5.

Take the "book the laser cutter Friday" trace from last time, with one more step added — the confirmation:

  1. Step 1: model calls the calendar tool → result: "Friday is free."
  2. Step 2: model calls the safety-manual lookup → result: "eye protection required."
  3. Step 3: model calls the booking tool → result: "confirmed for Friday, 2pm."
  4. Step 4: model writes the final answer to the student.

At step 4, the model isn't just working from step 3's result. All three earlier calls and results are still sitting in the context, appended in order, because nothing has removed them yet.

Check yourself

Step 1: calendar tool called, result "Friday is free." Step 2: manual lookup, result "eye protection required." Step 3: booking tool called, result "confirmed for Friday, 2pm." At step 4 the model writes its final answer. Which of steps 1, 2, and 3's results are still in the context window when it writes that answer?

Show the answer

All three. The context window keeps everything appended during a session unless something explicitly trims it, so step 4's call carries steps 1, 2, and 3 along with it.

Between sessions: by default, nothing survives 3 min

Here's the catch to that growing context from Section 2: once a session ends, by default none of it survives. A new session starts with a completely empty context window, so without something deliberately saved outside it, the assistant has no memory at all of the conversation that just happened (addyosmani/agent-engineer, Memory and context).

This isn't a bug to be fixed later — it's how these systems are built. The model itself holds nothing between calls; every call is self-contained, and "remembering" anything across a gap in time requires the surrounding program to have written it down somewhere durable first.

Think about IT work: a server process that restarts loses anything that was only sitting in RAM. Whatever never got written to disk is simply gone when the process comes back up; a crash, a deploy, a nightly restart — it doesn't matter which, the result is the same empty slate. The assistant works the same way — each new student visit is, in effect, a fresh process, and last visit's conversation is gone unless something explicitly wrote it to disk (or a database) before the session ended.

This isn't wasteful by accident, either. A session that always starts empty is cheap and simple to run: no server has to keep every past conversation loaded and ready, which matters when your model budget is small. The cost of that simplicity is that memory becomes something you have to build on purpose — nothing to look up means nothing to forget, but also nothing to remember.

So within a session, Section 2's rule holds: the context only grows. Across the boundary between sessions, the opposite is true by default: the context resets to nothing. Holding both of those at once — growing within, wiped between — is the single most useful fact in this lesson for arguing your design at review.

Check yourself

Riley booked the laser cutter on Monday. On Wednesday, a new session starts when Riley walks in again. Does the assistant know about Monday's booking?

Show the answer

Only if it was saved outside the window and gets retrieved into Wednesday's fresh, empty context. Nothing carries over on its own — that's exactly the gap retrieval and notes exist to fill, which is where Sections 4 and 5 go next.

Retrieval: pulling in just the relevant piece on demand 4 min

Retrieval is how memory across sessions mostly works in practice: the surrounding program saves information in durable storage, then fetches just the relevant piece back into context exactly when it's needed, instead of loading everything, every time (addyosmani/agent-engineer, Memory and context).

Why not just paste the whole manual in every call, now that windows are huge? Two reasons. First, cost: every token sent is a token you pay for, so a 90,000-token manual on every single request adds up fast on a small sponsor budget. Second, accuracy: as unrelated text piles up, models can actually get worse at using the part that matters — sometimes called the "lost-in-the-middle" effect. Retrieving just the relevant piece is usually both cheaper and more reliable than stuffing everything in (Redis, LLM context windows).

Put rough numbers on it: a 300-page manual might run about 90,000 tokens, while the one page that answers a given safety question might run about 300. Fetching that one page instead of the whole manual is roughly 300 times fewer tokens on that call — a real difference against a small sponsor budget, multiplied by every single question the assistant ever answers.

Back to the cookbook: a good index lets you flip straight to the one page you need instead of reading the whole book before you cook. Retrieval works the same way for the assistant — it looks up the one manual page the safety question is actually about, instead of loading all 300 pages for every request, and it can look up a completely different page next time a different question comes in.

Retrieval is also what makes "remembering across sessions" practical, given Section 3's empty-window rule: it's the mechanism that goes and gets one specific saved fact — a manual page, a past booking, a training note — and inserts it into the new, empty context window, instead of trying to load everything that was ever saved.

Check yourself

The manual is 300 pages. For a given safety question, should the assistant put the whole manual into context on every request, or retrieve just the one relevant page?

Show the answer

Retrieve just the one relevant page, on demand, each time a question needs it. That's cheaper per call and keeps the model focused on the fact that actually answers the question.

Notes: the agent's own summaries as memory it writes and rereads 5 min

Retrieval isn't limited to looking up a manual someone else wrote. An agent can also keep its own memory through note-taking: writing short summaries or logs to a file outside the context window, which get read back in later. It's a lightweight technique — no database required (Anthropic, Effective context engineering for AI agents).

Notes also solve a problem from Section 2: a long-running session's context keeps growing until it risks overflowing the window. Two fixes handle that. Compaction summarizes older turns into something shorter, keeping the key facts while dropping the play-by-play. Context editing clears out stale tool results that are no longer needed. Both let a long session keep going without losing the facts that matter (Anthropic, Effective context engineering for AI agents).

Check yourself

The assistant's session with a student has run long: forty tool calls deep, and the window is getting full. The assistant compacts the older turns into a short summary so the session can keep going. Does that compacted summary also make it into the next student visit's context, on its own?

Show the answer

No. Compaction keeps one long session usable by shrinking its own history; it has nothing to do with the next session. Only a note, written on purpose and retrieved later, crosses the gap between sessions.

Picture a data-science lab notebook: instead of rerunning an experiment from scratch to remember what happened, you write one entry after it and reread that entry next time, rather than redoing the whole experiment. The makerspace assistant can do the same thing: after Riley's visit, it writes one line — "Riley: laser training incomplete" — to a file, once, and rereads that line the next time it's relevant, instead of re-deriving Riley's training status from scratch every visit.

Notice what notes do not need: no database server, no special infrastructure, just a file the assistant can write to and a way to look it up later by something like a student's name. That's why it's described as lightweight — it's the cheapest form of memory available, and often the first one worth building.

Compaction and notes solve different problems that can look similar. Compaction keeps one long session usable by shrinking its own history. A note is written on purpose to be read in a different, later session. Mixing them up is an easy trap: a session that compacts its history well still starts from zero next time, unless something was also written out as a note.
Check yourself

Last week the assistant wrote a note about Riley's training status. This week, a different student asks about booking the laser cutter. Is last week's note automatically sitting in this session's context, or does something have to go fetch it?

Show the answer

Something has to fetch it. Writing the note is only half the job — a later step must retrieve its text and insert it into the new session's context, or the note is never seen again.

Common mix-ups, quick-fire 2 min

Five traps that catch people new to this, with the one-line fix for each. Nothing new here — just the ideas above, hit fast. For each one, ask yourself whether you'd have caught it before today's lesson.

"A bigger context window means I don't need memory or retrieval."
Tempting, since today's windows are huge — hundreds of thousands, even millions of tokens. Wrong: cost still scales with every token sent, and accuracy can still drop as irrelevant text piles up — Section 4.
"The model remembers me from last time we talked."
Tempting, since chat apps feel continuous from one visit to the next. Wrong: the model holds nothing between calls; any apparent memory is the surrounding program re-inserting saved text — Section 3.
"Context window and memory are the same thing."
Tempting, since both answer "what does the model know right now." Wrong: the window is the per-call budget; memory is the external storage and retrieval system that decides what gets put into that budget — Sections 1 and 4.
"Writing a note is enough; the agent will just know it later."
Tempting, since saving feels like the whole job. Wrong: something must still explicitly fetch that note's text and insert it into a later context window, or it's never seen again — Section 5.
"Once the window fills, everything so far is safely remembered somewhere automatically."
Tempting, since it feels odd for a computer to just forget. Wrong: without deliberate compaction or notes, trimmed or dropped content is simply gone — Sections 2 and 5.

Worked example and practice 5 min

Let's trace the makerspace assistant end to end, across two sessions, and watch exactly what's in context, what's retrieved, and what's noted at each point. This pulls together every section above into one real request, the way you'd actually have to reason about it at a design review.

Worked example — Session 1, Monday

Riley walks up and asks: "Is the laser cutter free Friday?"

  1. Context at the start: just the system prompt and the tool definitions — the conversation history is empty, since this session just began. This is the "empty window" from Section 3, before anything has happened yet.
  2. Step 1, calendar check: the model calls the calendar tool; the result, "Friday is free," is appended to context, exactly as Section 2 described — it doesn't replace anything, it stacks on top.
  3. Step 2, retrieval: the model retrieves one page of the safety manual for the laser cutter's rule, rather than the whole 300-page manual. That one page's text — "eye protection required, training required" — is inserted into context; this is Section 4's retrieval in action.
  4. Step 3, booking: the model calls the booking tool; it comes back "confirmed for Friday, 2pm," appended to context, same as every step before it, so the context now holds all three tool results plus the manual page.
  5. Step 4, note: the model answers Riley, then writes one line to a file outside the context window: "Riley: laser training incomplete, booked Friday 2pm." That's Section 5's note-taking — written once, on purpose, for a session that hasn't happened yet. It is not reread this session; its whole point is to be reread later.
Your turn — faded practice

Session 2: a few days later, Riley walks in again and mentions the laser cutter. You already have Session 1 fully worked above, with no steps given for this one. Using what you've learned in Sections 1 through 5, fill in all three, unaided:

  1. What is in context at the very start of Session 2, before anything happens?
  2. What, if anything, needs to be retrieved for Riley's new mention of the laser cutter, and from where?
  3. Is Monday's booking remembered in Session 2? If so, how exactly does that happen — if not, why not?
Show a solution

1. Just the system prompt and tool definitions again — a brand-new, empty context window, same as Session 1's start. Nothing from Monday's session carries over on its own; that's Section 3's rule, and it applies here exactly the same way.

2. The note written on Monday, "Riley: laser training incomplete, booked Friday 2pm," needs to be retrieved from wherever it was saved — something has to look it up, most likely by Riley's name, and insert its text into this new session's context before the model can use it.

3. Only if that note gets retrieved. If it does, the assistant "remembers" the booking and the incomplete training through the note's text sitting in context, not through any memory the model itself holds — if the note isn't retrieved for some reason, the assistant has no idea Monday happened at all, even though it wrote the note itself.

Summary 1 min

  • The context window is finite, shared, token-counted, and exists fresh for each call.
  • Within one session, the loop keeps appending each step's call and result — the context only grows.
  • Across sessions, by default nothing survives; a new session starts empty.
  • Retrieval fetches the one relevant saved piece into context, on demand, instead of loading everything.
  • Notes are memory the agent writes itself — and someone, or something, still has to reread them.
